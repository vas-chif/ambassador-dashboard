## 🛡️ **§2.1 Anti-XSS (Security & Sanitization) - REGOLE OBBLIGATORIE**

### 🚨 **REGOLA #1: MAI fidarsi dell'input utente!**

Tutti i dati provenienti dall'esterno (input utente, messaggi chat, motivazioni log, ecc.) DEVONO essere sanificati prima di essere renderizzati nel DOM o salvati in collezioni di audit che verranno visualizzate da altri admin.

### **Utility Ufficiale di Progetto**
Utilizzare esclusivamente la funzione centralizzata:
- **File**: [shared/utils/security.ts](file:///home/chif-vas/webpage_client/ProfessioneSiCura/ProfessioneSiCura-Unified/shared/utils/security.ts)
- **Funzione**: `escapeHTML(str: string | null | undefined): string`

### **Quuando usare `escapeHTML` (OBBLIGATORIO):**

1. **Rendering Dinamico**: In Vue, ogni volta che si usa `v-html` o l'attributo `innerHTML`.
2. **Log di Sicurezza**: Prima di salvare motivi o descrizioni in `auditLogs`, `setupActivationLogs`, ecc.
3. **Cloud Functions**: Quando si preparano stringhe per notifiche o email che contengono dati utente.
4. **Visualizzazione Tabelle**: Nelle tabelle admin (es: pannelli di Audit) se il dato non è già stato sanificato in fase di scrittura.

### **Esempi di Codice**

```typescript
// ✅ CORRETTO - Importazione e utilizzo
import { escapeHTML } from '../../../../shared/utils/security';

const safeReason = escapeHTML(userInputReason);
await addDoc(collection(db, 'auditLogs'), { reason: safeReason, ... });
```

```vue
<!-- ✅ CORRETTO - Rendering sicuro -->
<div v-html="escapeHTML(dynamicContent)"></div>

<!-- ❌ SBAGLIATO - Altissimo rischio XSS -->
<div v-html="dynamicContent"></div>
```

**NOTA**: L'uso di `{{ mustache }}` in Vue è intrinsecamente sicuro per il testo, ma `escapeHTML` resta obbligatorio per qualsiasi inserimento di HTML grezzo (`v-html`) o per la persistenza di logs leggibili via dashboard.

## 🛡️ **§2.2 Sicurezza Tripla (v-if vs Firestore Rules vs Cloud Functions) - REGOLE OBBLIGATORIE**

### 🚨 **REGOLA D'ORO: Il Frontend NON è Sicurezza**
Tutto ciò che viene fatto nel Frontend (es: `v-if`, `disabled`, `readonly`) serve esclusivamente per la **UX (User Experience)** e la pulizia dell'interfaccia. Un utente malintenzionato può sempre bypassare questi controlli tramite la console del browser o strumenti di rete.

Secondo le regole di conformità **GDPR Art. 32**, la sicurezza deve essere implementata su tre livelli indipendenti:

1.  **LIVELLO 1: Frontend (v-if / disabled / readonly)**
    *   **Scopo**: User Experience (UX).
    *   **Azione**: Nascondere bottoni, disabilitare checkbox, pulire l'interfaccia per evitare confusione.
    *   **Esempio**: Se la chat è disattivata, il tasto "Invia" scompare.

2.  **LIVELLO 2: Firestore Security Rules (Database)**
    *   **Scopo**: Integrità dei dati e autorizzazione fisica (La "Ferrovia").
    *   **Azione**: Bloccare la scrittura/lettura dei documenti se il toggle (globale o aziendale) è OFF. 
    *   **Risultato**: Anche se l'utente forza la comparsa di un componente via console, il database restituirà `PERMISSION_DENIED` al tentativo di salvataggio.

3.  **LIVELLO 3: Cloud Functions / Custom Claims (Backend Logic)**
    *   **Scopo**: Validazione logica di business e gestione permessi admin.
    *   **Azione**: Validare lo stato dei toggle prima di eseguire operazioni critiche (invio notifiche, promozione di nuovi admin, generazione di report).
    *   **Risultato**: Protezione totale contro tentativi di bypass che saltano l'interfaccia utente.

**REGOLA AI**: Ogni volta che implementi una restrizione visiva (`v-if`), verifica SEMPRE se è necessario aggiornare anche le Rules di Firestore o le Cloud Functions associate.

 * @param profile - User profile object to validate
 * @param requiredFields - Array of field names that must be present

 *
 * @remarks
 * - Used in registration wizard (step 3)
 * - GDPR compliance: validates fiscal code format
 * - Performance: <5ms for typical profile
 * - Cost: Zero Firestore reads (local validation only)
 *
 * @throws {ValidationError} If required fields are missing or invalid
 * @throws {TypeError} If profile parameter is not an object
 *

const validateProfile = (

  requiredFields: string[],
): ValidationResult => {
  const errors: string[] = [];
  for (const field of requiredFields) {

      errors.push(`Missing required field: ${field}`);
    }
  }
  return { isValid: errors.length === 0, errors };
}; /*end validateProfile*/

### **⚠️ Regole Critiche per Junior Developers**

1.  **Dist Directory**: Firebase Hosting cerca i file nella cartella `dist/spa`. Se il comando `yarn build` non è stato eseguito, Firebase caricherà una cartella vuota o darà errore.
2.  **Rewrites**: La regola `"rewrites": [{"source": "**", "destination": "/index.html"}]` è **FONDAMENTALE**. Serve per far funzionare Vue Router: senza questa, se ricarichi la pagina su `/auth`, Firebase darà errore 404.
3.  **Environment Variables**: A differenza di Netlify, Firebase Hosting NON legge le variabili dalla sua dashboard per il build. Le variabili `VITE_*` vengono iniettate **DURANTE IL BUILD LOCALE**. Assicurati che il tuo file `.env.production` sia aggiornato prima di lanciare `yarn build`.
4.  **Security Rules**: Il deploy dell'hosting non deploya automaticamente le regole di Firestore. Usa sempre `firebase deploy` o `firebase deploy --only firestore:rules`.

2. [x] **API Key Restrictions**: Se hai restrizioni sulle API Key, aggiorna i referrer HTTP includendo i nuovi domini Firebase.

## 🔒 **GitHub Branch Protection & Rulesets - OBBLIGATORIO**

### **🚨 REGOLA CRITICA: `main` Branch è PROTETTO**

**Dal 10 Dicembre 2025, il branch `main` ha regole di protezione ATTIVE:**

```bash
# ❌ VIETATO - Queste operazioni FALLIRANNO:
git push --force origin main          # ← ERRORE: GH006 Protected branch
git push origin --delete main         # ← ERRORE: Cannot delete protected branch
git commit --amend && git push origin main  # ← ERRORE: Must use PR

# ✅ WORKFLOW CORRETTO:
git checkout -b feature/my-feature    # Crea branch da main
git add .
git commit -m "feat: Add new feature"
git push origin feature/my-feature
# Poi crea Pull Request su GitHub UI
# Richiede: 1 approval + status checks passed
```

### **📋 Regole Attive su `main`**

| Regola                              | Stato     | Effetto                                            |
| ----------------------------------- | --------- | -------------------------------------------------- |
| **No force push**                   | 🔴 ATTIVO | Impedisce riscrittura history (git push --force)   |
| **No branch deletion**              | 🔴 ATTIVO | Impossibile eliminare branch main                  |
| **Require PR reviews**              | 🟡 ATTIVO | 1 approvazione obbligatoria prima di merge         |
| **Require status checks**           | 🟡 ATTIVO | Build + ESLint devono passare (GitHub Actions)     |
| **Require up-to-date branch**       | 🟢 ATTIVO | Branch deve essere aggiornato con main prima merge |
| **Require conversation resolution** | 🟢 ATTIVO | Tutti i commenti PR devono essere risolti          |
| **Block bypassing (admin)**         | 🔴 ATTIVO | Nemmeno owner può bypassare regole                 |

### **Configurazione Automatica di Continue URL**

**Problem**: Email verification URLs devono essere autorizzate in Firebase Console

**Solution**: App usa `VITE_AUTH_CONTINUE_URL` da `.env.{mode}`

**Esempio stagingFile** (`mobile/.env.staging`):
```env
VITE_AUTH_CONTINUE_URL=https://ps-staging-79d65.web.app/auth?mode=verifyEmail
VITE_FIREBASE_USE_EMULATORS=false
```

**Ejemplo local** (`mobile/.env.local`):
```env
VITE_AUTH_CONTINUE_URL=http://localhost:9000/#/auth?mode=verifyEmail
VITE_FIREBASE_USE_EMULATORS=true
```

**Come viene usata**: In [mobile/src/composables/useAuth.ts](mobile/src/composables/useAuth.ts#L83-L88):
```typescript
const continueUrl = import.meta.env.VITE_AUTH_CONTINUE_URL || 'https://professionesicura-mobile.web.app/auth?mode=verifyEmail';
const actionCodeSettings = {
  url: continueUrl,
  handleCodeInApp: true,
  // ...
};
await sendEmailVerification(userCredential.user, actionCodeSettings);
```
